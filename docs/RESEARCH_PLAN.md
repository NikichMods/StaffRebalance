# StaffRebalance — актуальный исследовательский план

**Контракт:** [REQUIREMENTS.md](REQUIREMENTS.md), решение 2026-11-07. Оплачивать выполненный staff-выстрел, не каждое HP-повреждение; возвращать энергию за подтверждённый melee-контакт, не за измеренную потерю HP; позволять штатному изменению damage влиять на parts/реакции/разрушаемые объекты. Реализация ещё не READY. Не возвращаться к blocked CALL 0x10C493C без нового доказательства безопасности.

## Первый проверяемый вопрос: штатный коэффициент Astral

**Вопрос:** существует ли на точном Steam 1.09 / UE4SS 83330635 безопасный штатный input, который можно изменить **при выполнении обычной Astral-атаки** так, чтобы она реально стала сильной/слабой, сохранив ванильные таланты и собственные обновления коэффициента?

1. Из уже извлечённых Skill/Timeline/Projectile и UHT проследить обычный Astral 1/2/3 от создания до чтения final source input; проверить разницу DamageRate, SetBaseDamageRate и иных уже найденных полей. Не исследовать весь EXE повторно.
2. На точном Blueprint hilda_staff_bolt_astral сопоставить offset 1263–1397 (talent_e804, Original Damage Rate и временное умножение на 1.1) и offset 1100 (восстановление). Установить, где технически могла бы применяться наша величина **без стирания** собственным writer игры; проверить момент native snapshot, если он решающий. Нельзя считать единичную запись в поле готовым решением.
3. Для каждого реально подтверждённого high-level seam проверить фазу (до расчёта), область действия (атака vs чужие источники), изменения damage по частям тела/окружению, сохранение самостоятельных статусов/AP/контроля и совместимость с vanilla talents. Изменение вторичных числовых эффектов **разрешено**, не требуется combat HP-only разделение.
4. Отдельно установить минимальный наблюдаемый момент *совершённого выстрела* для однократного расхода: skill input не равен commit, но источник/атака может быть достаточным. Мультиснарядная серия не должна тратить стоимость по числу снарядов; не создавать универсальный attack-token framework без доказанной необходимости.
5. Завершить этап точным вердиктом: минимальный проверяемый вариант, требующий одного короткого read-only/controlled runtime-теста, либо NO VERIFIED SEAM с конкретной причиной. Без создания DLL, native detour, новой системы хуков или смены продуктовых правил.

**Критерий достаточности:** локализован фактический владелец параметра, его final reader/writer, инварианты и одна узкая схема испытания. Только после этого разрешается подготовить неинвазивный тест по RUNTIME_TEST_HARNESS.md. Само наличие UFunction/поля не даёт READY.

## Следующие независимые границы (после первого ответа)

- **Melee credit:** найти безопасное событие настоящего попадания по врагу для доступного melee-оружия Хильды, с проверкой источника/цели, отсутствия начисления за воздух/сцену и двойного учёта; точный HP commit не требуется. Разные награды по типу атаки — параметр баланса.
- **Fire и остальные источники:** оценить реальное влияние слабого коэффициента на всю базовую атаку, особенно hilda_staff_bolt_fire_explosion. Не строить наследование по всем child actors заранее. Ice/Thunder live-тестировать только после штатной разблокировки.
- **Rest/lifecycle и HUD:** использовать уже наблюдённую пару запроса/восстановления Conduit. Отдельно решить save/load/death и наглядную обратную связь; не вводить пока отдельный файл пользовательских настроек для изменяемого runtime-состояния.

## Стоп-условия и разделение статусов

- **Game design** принят; **implementation mechanism** остаётся не доказан; **production gate BLOCKED** до per-change readiness и реального игрового PASS.
- Не возвращаться к отложенному нативному CALL 0x10C493C, CDB hardware breakpoints или broad damage rewrites только из-за отсутствия более простого решения.
- Если минимум зависит от выбора новых игровых компромиссов, сформулировать последствия для пользователя до изменений. Не выдавать исторический NO VERIFIED IMPLEMENTATION PATH строгого HP-контракта за вердикт для нового дизайна.
- История предыдущих планов сохранена в Git, в [feasibility review](DAMAGE_RESERVE_SEAM_FEASIBILITY_01.md) и [исходном runtime ТЗ](RUNTIME_OBSERVATION_TASK_01.md); старые планы точного HP-учёта и токенов атак не действуют.
