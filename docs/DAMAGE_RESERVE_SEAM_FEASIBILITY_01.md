# Damage reserve — выбор минимального места вмешательства 01

**Статус:** SOURCE-LEVEL PARTIAL / **production BLOCKED**. Принятая механика — непрерывный резерв усиленного **боевого HP-урона** ([REQUIREMENTS.md](REQUIREMENTS.md)). Проверены уже сохранённый native Astral report и **точные исходники** UE4SS `83330635`; **нового локального анализа EXE, игрового запуска, hook-кода или production-патча в этом шаге нет**. Это контрольная точка выбора механизма, не implementation READY.

## Что уже доказано, а что не следует из доказательств

- [ASTRAL_NATIVE_HP_PATH.md](ASTRAL_NATIVE_HP_PATH.md) (EXE SHA-256 `ddea6b5ca5d34836f01702993d20209c2595367287e6cd5a135a7ace1958b1c0`) статически прослеживает **обычный положительный Astral hit**: цель проверяется как `GenesisCharacter`; в `0x10C53E0` временно помещаются исходный projectile (`+0x218`) и hit-component (`+0x220`); вызывается расчет `0x10C44F0`, внутри — `0x10CEE30`, `ProjectileHitEvent` на `0x10C4656`, затем после дополнительной ветви — отрицательная дельта через call-site `0x10C493C` в writer `0x10C1C60`. Прямая сценическая ветвь находится отдельно. Эти RVA привязаны к указанному точному билду, их семантика за пределами исследованного пути **не установлена**.
- Событие `GenesisCharacter.ProjectileHitEvent` принимает **копию** `Damage`. Смена Lua-аргумента не доказана способом изменения последующей нативной величины. Событие может пригодиться для read-only доказательства пути; не считать его production writer.
- В [точном `LuaMod.cpp` UE4SS `83330635`](https://github.com/UE4SS-RE/RE-UE4SS/blob/83330635/UE4SS/src/Mod/LuaMod.cpp) `RegisterHook` регистрируется для загруженной **UFunction**, с отдельной native pre/post и script post семантикой. Он **не предоставляет универсального hook любого RVA**. Ранее полученные нулевые `RATE_CALL` согласуются с прямым, а не отражённым вызовом getter `0x10B0130`; отсутствие callbacks само по себе не доказывает отсутствия нативного выполнения.
- [`CppUserModBase.hpp`](https://github.com/UE4SS-RE/RE-UE4SS/blob/83330635/UE4SS/include/Mod/CppUserModBase.hpp) и [официальное руководство создания C++-мода](https://github.com/UE4SS-RE/RE-UE4SS/blob/83330635/docs/guides/creating-a-c%2B%2B-mod.md) дают поддерживаемый жизненный цикл C++ DLL. **Это не готовый и не проверенный inline-detour** нативной функции Asterigos. Понадобится отдельная обоснованная техника инструментирования конкретного места с ABI, сохранностью регистров, конкуренцией вызовов, отключением и version guard.
- `0x10C1C60` является **общим writer**: через него проходят также отдельные маршруты `GameGlobal.AddHP` и `SetHP`. Безопасно масштабировать все его вызовы нельзя: сюда могут попадать лечение, scripted changes и иные unrelated события. `GameGlobal.DamageCharacter_Cpp` — другой путь и не доказанная точка перехвата исследованного projectile.

## Три места — выбор по минимальному реальному blast radius

| Путь | Что даёт | Проблема и предварительный вердикт |
| --- | --- | --- |
| **A. Участок внутри `0x10C44F0` после защиты и до уведомления/записи** | Видна цель и в ходе вызова доступен projectile; потенциально одно изменение штатного рассчитанного числа до дальнейших потребителей | **Приоритетный кандидат для точной локализации.** Не доказано, что одно изменение распространяется одновременно на видимый урон и итоговую дельту; после уведомления есть ветвь с обнулением. Нужны живые регистры/локальные величины и разбор use-def chain, без патча. |
| **B. Только конкретный call-site `0x10C493C` перед writer** | Возможна изоляция от других вызовов общесистемного писателя; ветвь после расчёта и части условий | **Резервный кандидат.** Нельзя обещать согласование числа урона в UI/событиях (уведомление уже было). Также нужна проверка фактического контекста projectile и идентичности, а не подмена общесистемного writer. |
| **C. Универсальный `0x10C1C60` или source-level `DamageRate`** | Один writer / простые отражённые свойства | **Не выбирать по умолчанию.** Writer слишком широк, source-level rate штатно перезаписывается талантами и может влиять на сценические объекты. Рассматривать вновь только при доказанной узкой изоляции, а не из желания избежать нативного кода. |

**Решающее неизвестное** — существует ли внутри **одного** native character-damage call узкий этап, на котором после всех отмен/защит известны (а) проверенный источник staff/melee, (б) допустимая к изменению сумма HP, (в) итоговая запись и потребитель числа урона. Из известных RVA этого вывести пока нельзя. **Не запускать production-инструментирование, считая этот этап найденным.**

## Алгебра для проверки семантики резерва, не готовая формула игры

Для проверки граничных случаев обозначим: `D` — **штатная** неотрицательная сумма повреждения для одного боевого consumer после защиты, `H` — HP цели до применения, `w` — коэффициент слабого урона (0…1), `E` — доступный резерв, `k` — единиц резерва на единицу **реально применённого дополнительного HP-урона**. Конкретные числа не приняты.

- Слабая часть: `W = w * D`.
- При наличии энергии максимум предварительного усиления: `A = min((1-w)*D, E/k)`.
- Сумма на входе HP writer в упрощённой модели: `D' = W + A`.
- **Если** writer просто ограничивает исходящие повреждения текущим HP, фактическое усиление относительно слабой базы: `U = max(0, min(H,D') - min(H,W))`.
- Тогда `E' = E - k*U` с отсечкой к допустимым границам; для melee `E' = min(Emax, E + g*actual_melee_HP_loss)`, где `g` открыт.

Для наглядности **только числовая проверка алгебры**, без игровых измерений: `D=100, w=0.2, k=1`. При `H=100,E=30` получаем `D'=50, U=30, E'=0`. При `H=35,E=80` получаем `D'=100`, реальную потерю `35`, `U=15` и `E'=65` — взимать все `80` за overkill нельзя. При `H=10,E=80` слабая часть `20` и так убивает: `U=0`, расход отсутствует. Эти примеры проверены отдельным арифметическим расчётом, **не игровым тестом**.

**Критическая граница:** native report фиксирует дополнительную развилку, способную обнулить damage **после** `ProjectileHitEvent`. Простое списание энергии по предварительно вычисленному `D'` может неправильно тратить ресурс при блокировке, overkill или отмене фактической записи. Даже если один narrow hook меняет `D`, возможно потребуется **проверить реальный HP commit после штатного writer** в рамках того же call и только затем подтвердить расход. То есть «один локальный участок боевого расчёта» не обязательно означает «один callback»; не делать скрытых глобальных компенсаций после урона. Финальная политика округления и событие для HUD остаются открыты.

## Следующая необходимая проверка — только локальные данные EXE

**Метод:** повторно использовать локальный PE exact hash и уже существующий дизассемблер/reader. Нужна **одна ограниченная статическая проверка use-def и call-site**, а не новый дамп, общий hook или пользовательский игровой прогон.

1. В `0x10C44F0` установить, где живут calculated `D`, target component и provenance projectile до `0x10C4656`, после дополнительной развилки и перед `0x10C493C`; что из этих значений живёт после native writer. Отдельно определить источники UI/damage-number, если из локальных xrefs это возможно.
2. У `0x10C53E0` подтвердить период действительности `+0x218/+0x220`, восстановление исходного projectile и поведение reentrancy. Нельзя полагаться на thread-global «последний снаряд» без доказательства.
3. В `0x10C493C` / `0x10C1C60` проверить контракт передаваемой signed delta, условия фактической записи и доступность `HP_before/HP_after` в границе того же вызова. Проверить, нет ли побочных действий до clamp/commit, которые сломает изменение суммы.
4. Оценить по **конкретным xrefs** может ли та же узкая `character damage` ветвь обслуживать хотя бы базовый melee source; если нет — назвать ближайший отдельный путь. Для Fire/Ice/Thunder/DoT не экстраполировать по Astral: пока достаточно конкретной границы доказательства, полный охват на следующем этапе.
5. Сравнить техническую цену: один патч локального значения/сигнатуры или per-call native detour; возможность безопасно отказаться при неизвестном exe/ABI, не вмешаться в unrelated путь и снять инструментирование. **Не писать и не запускать detour в этом исследовании.**

**Достаточный результат:** одна кандидатная точка с подтверждённой инструкционной цепочкой, реальным контекстом источника/цели, порядком относительно уведомления и writer, областью вызывающих путей; либо точная причина, почему ни A, ни B не дают безопасного одностороннего изменения. При неудаче пересмотреть архитектуру прежде чем строить сложную native-инфраструктуру. Не требовать как prereq уникальный attack token: текущая продуктовая модель его отменяет.

## Production gate — по-прежнему BLOCKED

Observable property принят: плавный бюджет усиления по применённому combat HP с melee-пополнением. Для READY отсутствуют подтверждённые безопасный модифицируемый final consumer, классификация staff/melee по действительному источнику включая delayed/child, атомарный учёт реального HP delta, проверенный охват и тест без регрессий для мира/эффектов. Никакого обновления `main`, релизного номера, установки и live-утверждения этот документ не разрешает.
