## Точки наблюдения и границы

Перед каждым захватом на EngineTick проверяются точный путь UFunction, native/static признаки, отсутствие `FUNC_HasOutParms`, типы, имена и порядок полей. На этом UE4SS Lua не предоставляет полный набор CPF flags. Формы взяты из сохранённых UHT/cooked деклараций, а проверка отражения в игре выполняется самим observer перед регистрацией. Отсутствующие или несовпадающие функции дают `SKIP`. Ошибка регистрации или callback останавливает захват. Скриптовые callbacks имеют фазу post, а обе фазы native getter видны только при фактическом прохождении через соответствующую точку UE4SS. Все callbacks возвращают nil. [Ревизия UE4SS 83330635](https://github.com/UE4SS-RE/RE-UE4SS/blob/83330635/UE4SS/src/Mod/LuaMod.cpp).

| Точка | Что можно сопоставить | Ограничение |
| --- | --- | --- |
| `GenesisCharacter.BeginSkillStateEvent / EndSkillStateEvent` | Границы состояния и имя skill для playable Hilda | Базовая декларация может не исполняться через доступный script callback. Имя состояния не является ID исполнения |
| Точные `ReceiveBeginPlay` для Astral/Fire bolt, arrow/damage, Fourth Astral hit и dual actor | ID класса и адрес источника, владелец, skill в момент наблюдения | BeginPlay post позже выделения объекта. Владелец может быть ещё недоступен. Fire explosion использует общий `sphere_200`, исключённый из захвата этой версии. Dual hook требует собственного загруженного override |
| `BaseProjectile.CharacterHitted` | Скалярный damage и flags уведомления от источника игрока | Цель и момент изменения HP из этой сигнатуры не следуют |
| `BaseProjectile.GetBaseDamageRate` | Порядок естественных reflected pre/post обращений для выбранных классов | Observer сам этот getter не вызывает. Обход отражения оставляет пробел. Значение native return и принадлежность вызова финальному расчёту не измеряются |
| Отдельный Conduit захват | `Interact_Rest`, `Interact_EndUse`, `Interact_Transport`, `MainGameInstance_BP.RecoverPlayerAndScene`, `GTGameHUDBPLocal.EventOnRestEnd` | Фазы script post. Нет автоматической классификации общего recovery как успешного отдыха |

У `SpawnProjectile` есть два struct reference, у `SpawnProjectileEX` ещё выходной массив. В `ProjectileOverlapCharacter/Scene/GameEventObject` и `ProjectileHitEvent` есть struct параметры. Даже callback, игнорирующий их, не избавляет UE4SS от подготовки аргументов. Эти пути исключены. Поэтому observer регистрирует источники и доступные уведомления, а direct HP delta и pre-write остаются пробелом. Если после прогона порядок останется неразличим, следующий узкий метод — локализовать native обработчик конкретного Astral попадания по связке scalar `CharacterHitted` и полю `CharacterAttributeComponent.HP`. Сначала нужен наблюдённый trace, чтобы выбрать участок. Глобальные damage/ProcessEvent hooks и чтение произвольных адресов не используются.

В callbacks остаются только краткоживущие обёртки, а между вызовами сохраняются скаляры. Адрес — подсказка для сопоставления в одном коротком захвате, без гарантий уникальности после переиспользования. При ошибке либо лимите callbacks становятся инертными. Удаление собственных hooks происходит на EngineTick по stop или deadline. Native cleanup может завершиться при следующем проходе native post согласно исходнику UE4SS.

## Проверка и первый игровой прогон

Офлайн выполнен исходный Lua файл в Lupa Lua 5.4 на строгих подстановках отражения и callbacks. Проверены отказ при out/struct форме, фильтр владельца, обработка ещё неизвестного owner, nil-return, порядок записей pre/post, раздельное включение combat/rest, игнорирование старых callbacks, остановка на ошибке, по времени и на 120 событиях, снятие регистрации по stop. Подстановки проверяют логику скрипта. Игровой ABI, доступность загруженных функций и момент записи HP требуют живого свидетельства.

После установки и только в отдельном сеансе:

1. Загрузись за Хильду с посохом. `Ctrl+Shift+F8` открывает захват до 120 секунд. Сделай один промах, обычную серию с попаданием и один Charged Rays. Если доступно, сначала войди в прицел и отмени его без выстрела. `Ctrl+Shift+F10` завершает захват.
2. У Conduit включи `Ctrl+Shift+F9`. Открой и закрой меню, затем отдохни. Телепортацию проверь в этом же захвате последней, если она доступна. `Ctrl+Shift+F10` завершает захват. Таймер rest рассчитан на 90 секунд.
3. Закрой игру и сообщи, какие действия удалось выполнить. Codex сверит строки `STAFF_COMBAT_OBS01` в закрытом UE4SS.log, идентичность установленного исходника и затем отключит observer.

Повторный захват возможен после stop. Если класс не загружен, первый захват отмечает это, а повтор после обычного действия даёт второй шанс на точную регистрацию. Fire/AoE, особые таланты и melee имеют смысл в следующих отдельных захватах, если первый прогон покажет рабочую точку наблюдения. Доказательство безопасного изменения только боевого HP по-прежнему требуется перед production.

## Подготовка короткой проверки доставки событий — прогон 02 (без runtime-подтверждения)

**Установлено при закрытой игре 2026-11-05.** Пользователь подтвердил приёмку HildaSoftLight 0.1.0 и разрешил установку observer. Активирован точный Git blob из `e64734fdb9043a8739f44af1f300fa1632d388ce`. SHA-256 установленного Lua `07b8a3b2eb48a2cbb8c0aea6f626b7efe386f56461563821465f4758dc8b3ea7`. Предыдущий Lua сохранён локально. Хеш `mods.txt` совпал до и после активации. Ожидается короткий игровой тест.

После прогона 01, где наблюдался только `ARMED`, в исследовательский observer внесена **только диагностика маршрута управления**. Прошлый результат остаётся неизменным; причина разрыва ещё не установлена. Исходник: [`research/combat-observation-01/StaffRebalanceCombatObserver/Scripts/main.lua`](../research/combat-observation-01/StaffRebalanceCombatObserver/Scripts/main.lua), зафиксирован в той же исследовательской ветке.

- `ENGINE_TICK_PING_RETURNED` означает, что разовая постановка задачи из startup вернулась без Lua-исключения; `ENGINE_TICK_PING_ENTRY` отдельно подтверждает, что задача действительно исполнилась.
- `KEY_CALLBACK key=F8/F9/F10` фиксирует фактический вход в назначенный обработчик.
- `DISPATCH_RETURNED key=...` означает только возврат из `ExecuteInGameThread` без Lua-исключения; **не** подтверждает, что callback исполнился.
- `ENGINE_TICK_ENTRY key=...` подтверждает реальный вход в поставленный обработчик на EngineTick. После него существующие `CHECKED`/`SKIP`/`HOOK`/`CAPTURE`/`ERROR` локализуют последующую фазу.
- Эти метки могут записаться в другом порядке между потоками; сопоставлять их по `key`, а не предполагать неизменный порядок `DISPATCH_RETURNED` и `ENGINE_TICK_ENTRY`.

**Ограниченная процедура:** Codex после проверки актуальной исследовательской ветки и DevRules устанавливает точный Git blob обновлённого Lua в уже существующий observer при закрытой игре, проверяет хеш и включает только его `enabled.txt`. Пользователю достаточно открыть игровую сессию, нажать `Ctrl+Shift+F8`, затем `Ctrl+Shift+F10`, закрыть игру. Бой/отдых/телепортация **не нужны** до подтверждения маршрута захвата. Codex получает закрытый UE4SS.log, сохраняет SHA и результат в этом отчёте и отключает observer при закрытой игре. Если F8 привёл к `ERROR`/`SKIP` вместо `CAPTURE`, исследовать точное место, а не объявлять запуск боевого наблюдения успешным. Если `KEY_CALLBACK` отсутствует, не приписывать отсутствие `CAPTURE` механизмам боя.

## Подготовка альтернативного запуска после прогона 02 — клавиши без модификаторов

Прогон 02 подтвердил выполнение startup `EngineTick`, но **не** вход в `RegisterKeyBind` callbacks на `Ctrl+Shift+F8/F10`. Причина по-прежнему неизвестна. Для различения отсутствия всей доставки клавиш от проблемы с модификаторами в той же исследовательской ветке добавлен узкий **непроверенный в игре** диагностический вариант:

- `F6` **без Ctrl/Shift** запускает существующий combat `start("combat")`; `F7` без модификаторов вызывает существующие stop/cleanup. Старые `Ctrl+Shift+F8/F9/F10` остаются неизменными.
- Оба bare-key registrations вызываются только при отсутствии зарегистрированного UE4SS keybind для этой клавиши; занятая/недоступная клавиша даёт `BARE_KEY_UNAVAILABLE` и не ломает регистрацию существующих сочетаний.
- `BARE_KEY_REGISTERED` подтверждает завершение вызова `RegisterKeyBind`, **но не** доставку нажатия. `KEY_CALLBACK key=F6/F7` подтверждает его реальную доставку, `ENGINE_TICK_ENTRY` — исполнение задачи. Если эти метки отсутствуют, не приписывать это боевой системе.
- Поддержка bare `RegisterKeyBind(key, callback)` и значений `Key.F6/F7` проверена по [точному исходнику UE4SS `83330635`](https://github.com/UE4SS-RE/RE-UE4SS/blob/83330635/UE4SS/src/Mod/LuaMod.cpp); это **source-level** поддержка, не новый live PASS.

**Короткая проверка:** локальный Codex после проверки DevRules, фактического checkout и исходного лога устанавливает точные байты обновлённого Git blob, не затрагивая другие моды. В игровом окне нажать **F6**, затем **F7**, выйти; бой/отдых пока не нужны. Codex проверяет `BARE_KEY_*`, `KEY_CALLBACK`, `DISPATCH_RETURNED`, `ENGINE_TICK_ENTRY`, `CAPTURE`/`SKIP`/`ERROR`, фиксирует SHA лога и отключает marker при закрытой игре. Если окажется, что F6/F7 заняты, **не** вводить наугад другие сочетания без соответствующей проверки и основания. Не объявлять исправленным ранее наблюдённый сбой до runtime доказательства.

При успешном получении `KEY_CALLBACK` следующий узкий шаг зависит от того, произошёл ли `CAPTURE` или обнаружен точный preflight отказ. Production gate остаётся BLOCKED.

## Fire 02 — ProjectileHitEvent

UHT `GenesisCharacter.h:159` объявляет `ProjectileHitEvent(ABaseProjectile*, UPrimitiveComponent*, FVector_NetQuantize, float)`. На подтверждённом EXE нативная обёртка `0x1296DC0` кладёт аргументы в `+0x00`, `+0x08`, `+0x10`, `+0x1C`, разрешает имя события и вызывает виртуальный dispatch цели `+0x220`. В `BaseAICharacter_Mob_BP_C` найден собственный script override родительской декларации. У `m006_thugdagger_BP_C` и `m006_2_thugdagger_BP_C`, встречавшихся в предыдущем Fire-прогоне, собственного override нет. SHA-256 точечного экспорта `BaseAICharacter_Mob_BP` — `3164ca6926bea535acb01aeb71fdbde0587f1e9a4b859a28cd377795f026b8a3`. | Параметр cooked override | Тип | Offset | Размер |
| --- | --- | ---: | ---: |
| `projectile` | `ABaseProjectile*` | `0x00` | 8 |
| `hitComponent` | `UPrimitiveComponent*` | `0x08` | 8 |
| `hitPosition` | `/Script/Engine.Vector_NetQuantize` | `0x10` | 12 |
| `damage` | `float` | `0x1C` | 4 |

Все четыре — `Parm`, без `OutParm`, `ReferenceParm` и `ReturnParm`. На UE4.27 точный script hook использует post `ProcessLocalScriptFunction`. UE4SS проверяет script entry через `ProcessInternal` и до Lua callback передаёт свойства из `Stack.Locals()`. Struct pusher в режиме `GetParam` создаёт обёртку с указателем на данные и метаданными. Чтение полей требует последующего обращения. Observer не вызывает `get` для `hitPosition` или `hitComponent` и не удерживает обёртки. Этот вывод относится только к данной сигнатуре и UE4SS `83330635`, SHA-256 установленного DLL `ce5e3c46a920cc00b2817ac61e438c9162830290379d0b5b9c4dfc2b29459290`. [Регистрация и подготовка аргументов UE4SS](https://github.com/UE4SS-RE/RE-UE4SS/blob/8333063595fa3c49ad307f3b0f732accbb760d25/UE4SS/src/Mod/LuaMod.cpp), [struct pusher](https://github.com/UE4SS-RE/RE-UE4SS/blob/8333063595fa3c49ad307f3b0f732accbb760d25/UE4SS/src/LuaType/LuaUObject.cpp#L746).

Ограничения — 45 секунд и не более 120 событий. Callback читает только на игровом потоке. Цель — контекст override класса обычных мобов, без вывода о враждебности любого такого экземпляра. ## Melee Contact 01 — обычный удар кинжалами

**Research-method checkpoint.** Вопрос — доставляет ли уже проверенный mob `ProjectileHitEvent` исходный экземпляр кинжалов, владельца и цель, и какие события он даёт за один короткий сценарий. [Статика кинжалов](DAMAGE_RESERVE_SEAM_FEASIBILITY_01.md#melee--фактическая-потеря-hp-от-обычного-удара-кинжалами) установила общий character-contact маршрут, два `fire object` первого удара и пять возможных ключей одного класса. Старый combat-режим видит создание, а Fire-режим фильтрует кинжалы. Достаточно узкого режима существующего CombatObserver с двумя точными script post хуками и короткого игрового прогона. Используется проверенный Fire-контракт аргументов. Новый инструмент, запись HP и native hooks не нужны.

- `MELEE_SPAWN` даёт положительный контроль для промаха. `MELEE_HIT` пишет тот же идентификатор источника, `ProjectileDataName`, `GetCharacterOwner`, текущую Хильду, экземпляр mob-цели и hit component. `matched_source` относится только к классу, ключу и владельцу. Враждебность в прогоне устанавливается выбором обычного атакующего моба. Принадлежность к mob-классу сама по себе не доказывает враждебность всех экземпляров, а штатный `IsHostile` из callback не вызывается.
- Один взмах может дать два разных источника. Несколько целей и повторные уведомления разделяются при разборе по экземплярам источника, цели и компонента. Совпадение этих полей помечает повтор для исследования, но само по себе не отличает дубль от второго реального контакта. Адрес без FName недостаточен из-за повторного использования памяти.
- `ProjectileHitEvent` предшествует writer, поэтому поглощение **внутри writer** не может отменить уже выданное событие. Остаётся проверить, доставляется ли событие при конкретной ранней защите или отказе до этой точки. `Damage` логируется и может быть нулём. По его числу нельзя определить факт полного поглощения.

**Сценарий.** После загрузки с кинжалами рядом с обычными врагами сделать прогревочный взмах. Нажать F4. Выполнить по одному первому лёгкому удару в воздух и по одиночному обычному мобу, с паузой между атаками. Если рядом есть два моба, задеть обоих одним первым ударом. Известный полностью поглощающий сценарий проверять только при его естественной доступности. F7, выход из игры, затем разбор закрытого лога и отключение observer. У melee-режима нет таймера и общего счётчика для автоматической остановки. Захват ограничен точными источником и событием, F7 снимает оба хука.

**Граница вердикта.** Нужны подтверждённые `MELEE_SPAWN` на промахе без соответствующего `MELEE_HIT`, положительная цепочка на мобе и F7 со снятием обоих хуков. Несколько целей и полное поглощение отмечаются отдельно по реально доступным сценариям. До этого `ProjectileHitEvent` остаётся кандидатом для узкой атрибуции контакта кинжалов. Награда не начисляется.

**Локальная проверка.** Lua 5.4 с имитацией UE4SS прошёл синтаксис, фильтрацию класса и владельца, учёт разных имён при одном адресе, логирование нулевого Damage, повторных событий и нескольких целей, отказ на неверной форме параметров, проверку GameThread и снятие обоих хуков по F7. Имитация проверяет логику observer. Доставка самих игровых событий в melee остаётся открытой.

### Расширение фильтра целей первого удара кинжалами — 2026-11-08

**BLOCKED.** Melee Contact 01 подтвердил семь контактов с тремя атакующими экземплярами `m052_arvicolina_BP_C`. Dev на `d97023dc41162844462ec20cb5a954fc6b4bdae2` принимает post `BaseAICharacter_Mob_BP_C:ProjectileHitEvent` только для `hilda_dual_atk_C`, эффективного ключа `hilda_dual_attack_astral`, владельца, совпавшего с текущей Хильдой, и точного класса цели. - **Штатный допуск projectile шире враждебности.** Cooked `Projectile_Player/hilda_dual_attack_astral` имеет `AffectEnemy` (enum 0). На EXE Steam 1.09 / 12996889 с [ранее зафиксированным SHA-256](DAMAGE_RESERVE_SEAM_FEASIBILITY_01.md#melee--фактическая-потеря-hp-от-обычного-удара-кинжалами) сверены нативные проверки `0x10B7073` и `0x10C5B5F` → `0x10B8F70`. Для обычной цели этот helper сравнивает фракцию projectile с фракцией цели через `0x10CFAE0`. При `AffectEnemy` ветвь `0x10B8FF4–0x10B8FF6` принимает любое ненулевое отношение. `EFriendFlag` различает Friendly (0), Neutral (1) и Hostile (2), причём `0x10CFAE0` возвращает 1 и при отсутствии записи пары. Это граница проверки фракции, а не свидетельство фактического попадания по нейтральному NPC: прочие штатные проверки могут его исключить.
- **Минимальный кандидат на положительный допуск.** Считать допустимой цель только при явном направленном отношении `Hostile` от текущей фракции Хильды к текущей фракции цели. Сохранённые UHT-декларации показывают `GenesisCharacter.CharAttrComponent.faction` и `FFactionData.FactionList` из пар `FFactionPair` с `EFriendFlag`. Нативное чтение тега `0x114B510` только читает компонент и тег. Один тег, различие двух тегов или принадлежность к mob-классу не определяют отношение. `IsHostile(Hilda, target, false)` задаёт нужную семантику без hate-list, но штатный lookup `0x1121910 → 0x10F7360` может разрешить ресурс и записать слабую ссылку (`0x10F7444`). Из hit callback его не вызывать.

**Недостающее доказательство:** доступный из dev Lua read-only источник явного отношения `Hostile` для живой направленной пары фракций, эквивалентный штатному отношению без hate-list. Сохранённые данные подтверждают поля и семантику, но не дают проверенного пути чтения самой записи отношения из Lua. Неизвестная или отсутствующая запись должна давать пропуск.

Игру не запускали. Повтор удара по одному другому врагу сейчас показал бы доставку callback, но не закрыл бы пробел в определении враждебности. ## Общий обзор первых melee-атак

Действующий контракт больше не требует проверки фракций. [Dev-прогон](DEV_PROTOTYPE_01.md#игровой-результат-расширения-melee--2026-11-08) уже подтвердил кинжалы на двух mob-классах. Здесь проверяется, какие первые обычные удары всех пяти melee-оружий доставляют тот же `ProjectileHitEvent`, какие источники и пары видны и отделяется ли положительный контакт посохом от кандидатов melee. Условный счётчик 0/20 живёт только в наблюдателе.

Используется режим `survey` существующего CombatObserver. Сигнатура и offsets mob post hook совпадают с Melee Contact 01. Штатный `BeginDoSkill` для текущего аним-инстанса Хильды даёт дополнительную отметку действия. `GetDoingSkill` в hit/spawn — значение в момент вызова. Оно может уже отличаться от действия, создавшего источник. Exact `ReceiveBeginPlay` известных классов из cooked-таблиц подключаются в начале соответствующего этапа, если загружены и проходят проверку сигнатуры. Отсутствие spawn hook отмечается отдельно и не блокирует mob post. Новые нативные точки не вводятся.

**Порядок.** F6 включает захват. После экипировки и завершения переходной анимации F5 открывает очередной этап: кинжалы → копьё → молот → меч со щитом → боевые браслеты → обычный Astral-посох. На каждом этапе один первый обычный удар с подтверждённым попаданием по обычному противнику. Подождать конца атаки и доставки контактов перед F5. Для последнего этапа F7 закрывает захват. Один контрольный взмах после F7 даёт UE4SS возможность завершить снятие native pre/post `BeginDoSkill`. Выйти без сохранения и отметить любые промахи или лишние атаки.

`SURVEY_HIT` записывает все callbacks выбранного mob hook в окне, в том числе чужие и неатрибутированные. Потенциальный +1 требует совпадения stage, точного класса и строки из cooked-набора, владельца Хильды, mob-цели и новой пары. Неизвестный источник остаётся в логе с нулевым диагностическим кредитом для ручной классификации. Разные экземпляры источника считаются отдельно. `SURVEY_SUMMARY` даёт raw, unique, potential, capped reserve и число наблюдавшихся spawn. Потолок 20 ограничивает лишь reserve. Повтор пары подавляется в диагностическом кредите, но сам по себе не доказывает дубль одного физического контакта. Для посоха нужен положительный HIT от Хильды и нулевой credit.

**Офлайн Lua 5.4 mock PASS.** Проверены шесть окон, повторы одной пары, события сверх ёмкости, ноль для посоха, отсутствие необязательного spawn hook и вызовы снятия хуков. Это гипотеза, не доказательство для точного Lua source и HP; неизменные source, target, component и notified Damage сами по себе не устанавливают физическую кратность. Правило +1 за пару остаётся временным консервативным ограничением восстановления от DoT. Отдельное повторное нажатие может управлять той же сферой; сохранение/смена actor identity между действиями для него не измерялись. Не менять игровое начисление и не расширять тест только ради теоретически точного числа тиков без нового решения по балансу.
